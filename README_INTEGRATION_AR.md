# إضافة نظام التنسيق الذكي إلى تطبيق YouTube → Deepgram

هذه الحزمة تضيف منتجًا مستقلًا لتنسيق التفريغات باستخدام OpenCode وحساب ChatGPT، من دون تغيير مسار تنزيل YouTube أو Deepgram أو عمّال التفريغ الحاليين.

## ما الذي أُضيف؟

- عامل Celery مستقل باسم `formatting-worker` وطابور `formatting` بتزامن افتراضي واحد.
- خادم OpenCode داخلي محمي بـBasic Auth، مع Volume دائم لبيانات المصادقة.
- صفحة في الإعدادات لربط حساب ChatGPT وفصله واختيار النموذج ومستوى التفكير.
- صفحة مستقلة لرفع مهارات ZIP وفحصها واستخراجها وحفظ كل إصدار ببصمة SHA-256.
- زر **تنسيق بالذكاء الاصطناعي** بجانب كل تفريغ مكتمل.
- صفحة نتيجة مستقلة، وتنزيل الملفات الناتجة، وإعادة التنسيق كمحاولة جديدة.
- خمسة جداول PostgreSQL مستقلة: `formatting_skills` و`formatting_settings`
  و`formatting_jobs` و`formatting_outbox` و`formatting_artifacts`.
- Snapshot ثابت للنص والمهارة والنموذج ومستوى التفكير لكل محاولة.
- فحص مستقل للنتائج قبل النجاح، بما في ذلك بنية DOCX وصلاحية JSON ورأس PDF.

## الدمج الآمن

فك الحزمة في أي مكان، ثم نفّذ:

```bash
python scripts/apply_formatting_integration.py \
  /path/to/youtube-deepgram-transcriber \
  --expected-tree-sha256 <trusted-canonical-tree-sha256>
```

يرفض التطبيق المباشر مجلدًا بلا إقرار هوية افتراضيًا. يجب أن تأتي بصمة الشجرة من
سجل موثوق مستقل. إذا تعذر ذلك، لا يُقبل وضع المجلد إلا بالخيار
`--acknowledge-unverified-base` ذي التحذير الشديد؛ عندها يكون الفحص **بنيويًا فقط**
ولا يثبت إصدار خط الأساس أو سلامة محتواه. المسار المفضل هو Builder مع ZIP المرجعي.
هوية `formatting-integration-tree-v1` تشمل أسماء كل الملفات والمجلدات النسبية
المرتبة، بما فيها المجلدات الفارغة، وحجم كل ملف وبصمته؛ ولا تشمل Metadata النظام.

السكربت ينفّذ فحصًا تمهيديًا كاملًا قبل الكتابة، ثم:

1. يتحقق من بنية المصدر الأصلي الكاملة: إعداد Alembic وقوالبه، ووحدات
   `main.py` و`celery_app.py` و`db_wait.py` و`scheduler.py` و`core/db.py`
   و`core/models.py`، وملفات الواجهة `package.json` و`App.tsx` و`api.ts`
   و`hooks/useFetch.ts` و`pages/Jobs.tsx`. تبقى ملفات الأساس الجوهرية محفوظة
   ولا تنسخها حزمة الميزة فوق المصدر الأصلي.
2. يكتشف رأس Alembic الوحيد ويربط الترحيل الجديد به.
3. يفحص حافتي `down_revision` و`depends_on` لاكتشاف المراجع المعلقة والدورات
   والترحيلات اللاحقة، مع إبقاء تحديد الرؤوس مبنيًا على `down_revision` كما يتطلب
   Alembic، ويرفض القيم الملتبسة أو غير القابلة للتحليل.
4. يتحقق مسبقًا من إمكانية تعديل `main.py` و`App.tsx` و`Jobs.tsx` بأمان.
5. يحسب هوية شجرة خط الأساس وBytes كل هدف متوقع، ثم يأخذ قفل دمج حصريًا مجاورًا
   للمشروع بـ`O_CREAT|O_EXCL`. تحت القفل يعيد حساب هوية الشجرة ويفحص هوية/Hash كل
   هدف فورًا قبل Backup والاستبدال، ويرفض أي تعديل متزامن. القفل الموجود، ولو كان
   قديمًا، يوقف الدمج ولا يُحذف تلقائيًا.
6. ينشئ Backup لكل ملف موجود سيتغير، ويسجل جرد الملفات المنشأة والمستبدلة، ويسجل
   كل وجهة محاولة في `integration-backup.json` **قبل** استبدالها.
7. يضيف الأسطر المطلوبة إلى الملفات الحالية بدل استبدالها بالكامل.
8. يدمج اعتماديات API النصية الناقصة في `backend/requirements.txt`. إذا تطابق اسم
   حزمة بعد توحيد الأحرف و`-`/`_`/`.` فلا يقبل إلا قيدًا نصيًا مكافئًا تمامًا؛ أما
   اختلاف القيود فيوقف الدمج برسالة تطلب إنشاء قيد موحد يدويًا. لا يحاول السكربت
   أداء Resolver لحزم Python، ولا يعتمد على معاملة تثبيت Docker لاحقة لتجاوز تعارض.
   القيود الأربعة المكررة في حزمة الدمج مطابقة حاليًا، حرفيًا، لأسطر الملف الأساسي.
9. ينسخ ملفات الميزة الجديدة وCompose الموحد وDockerfiles وملف `.dockerignore` والوثائق.
10. لا يفتح أو يعدّل ملفات مهام YouTube أو Deepgram.

إذا وجد `docker-compose.formatting.yml` قديمًا عند أي عمق فإنه يرفض الدمج قبل أي
كتابة. انقل الملف أو احذفه يدويًا فقط بعد مراجعة إعداداته ونقل المطلوب منها إلى
`docker-compose.yml` الموحد، ثم أعد الدمج. لا يحذف السكربت الـoverlay بصمت.
كما يفحص الشجرتين كاملتين وكل أسلاف مسارات المصدر والهدف بـ`lstat`، ويرفض الروابط
الرمزية والمكسورة والصلبة وReparse Points والملفات الخاصة قبل Backup أو كتابة المشروع.

الالتزام مرحلي ومحافظ على الاسترداد، وليس Transaction كاملًا: يستبدل الملفات
مرحليًا بعد اكتمال النسخ الاحتياطي، ويحاول الاستعادة بملف مؤقت ثم `os.replace`.
يسجل الوجهة قبل كل محاولة، ويربط كل ناتج بهوية/Hash الملف المؤقت قبل الاستبدال؛
وعند rollback لا يحذف أو يستبدل إلا هدفًا ما زال يطابق الناتج المملوك للعملية.
إذا فشلت أي استعادة، يبقي مجلد `.formatting-integration-backup-*` ويبلغ مساره؛ لا
تحذفه حتى تستعيد كل الملفات يدويًا وتؤكد سلامتها، ولا تشغّل Verifier أو ترفع الشجرة.
بعد نجاح الدمج يبقى Backup حتى يراجعه المشغل ويزيله بنفسه. أرشفه كاملًا خارج جذر
المشروع وتأكد من إمكان قراءة الأرشيف، ثم احذف نسخته من الشجرة يدويًا. يرفض Verifier
أي Backup بهذا الاسم عند أي عمق.

بعد تأمين Backup خارج المشروع وحذفه من الشجرة، وقبل أي رفع أو نشر، شغّل الفحص
البنيوي (Verifier):

```bash
python scripts/verify_coolify_bundle.py /path/to/youtube-deepgram-transcriber
```

أي رسالة خطأ تمنع الرفع والنشر، لكن نجاحه لا يثبت أن Compose صالح تشغيليًا ولا أن
الصور تُبنى. يفحص Verifier الشجرة كاملة ويرفض، عند أي عمق،
الـoverlay القديم وBackup الدمج ومتغيرات البيئة السرية وملفات الاعتماد والمفاتيح
والشهادات وCookies والمصادقة وقواعد البيانات والكاش والحالة المحلية.

يتطلب الفحص `frontend/index.html` و`frontend/package.json` وLockfile واحدًا على
الأقل من الأنواع التي يدعمها Dockerfile. لا يخمن أسماء Vite/TypeScript الخاصة
بالمصدر الأصلي غير المتاح، ولذلك لا يستطيع إثبات اكتمال اعتمادات الواجهة بصورة
انتقالية. يجب أن تنفذ بوابة إصدار خارجية `docker compose config` وبناء جميع الصور
وبناء الواجهة والاختبارات والترحيلات قبل النشر.

بعد الدمج استخدم `docker-compose.yml` كمورد Coolify فقط بعد ضبط `APP_URL`
و`TRUSTED_HOSTS` ومفاتيح Deepgram والقيم اليدوية المطلوبة. ملف الإنتاج يثبت
Cookies الآمنة ولا ينشر Host port، ولذلك لا يمثل أمر تشغيل محليًا جاهزًا؛ يلزم
لذلك Override محلي منفصل وأسرار يدوية وIngress محلي.

## بناء ZIP مصدر كامل

عند توفر أرشيف المشروع الأصلي:

```bash
python scripts/build_full_source_from_original.py \
  youtube-deepgram-transcriber.zip \
  youtube-deepgram-transcriber-with-formatting.zip
```

يرفض السكربت دائمًا أن يكون `base_zip` هو `output_zip`. يجب ألا يكون المسار النهائي
موجودًا عند بدء البناء أو النشر؛ لا يوجد خيار overwrite إطلاقًا. اختر اسمًا جديدًا،
أو أزل الناتج القديم يدويًا قبل بدء Builder.

ينشئ السكربت بقرب الناتج قفلًا حصريًا ذريًا يبقى طوال البناء والإنهاء، ويرفض القفل
الموجود ولا يحذف قفلًا قديمًا تلقائيًا. يفتح ZIP المصدر مرة واحدة بعد رفض الروابط
والملفات الخاصة والصلبة، ويحسب بصمته ويفكّه من المقبض نفسه، مع إعادة فحص هوية
`dev/inode/size/mtime` والبصمة مباشرة قبل الفك وبعده. لذلك لا تُمرر حالة Verified أو
Alternate من Hash قديم لمسار أُعيد فتحه.

ينشئ Backup الاسترداد خارج شجرة المشروع المؤقتة، ثم يبني ZIP في حجر خاص بجانب
الناتج. بعد Verifier وسلامة ZIP والتنظيف يعيد فحص هوية الحجر وبصمته فورًا قبل النشر.
قبل إنشاء ZIP يثبت قائمة الملفات وهوية/Hash كل ملف. يفتح كل مصدر بمقبض no-follow
ثابت، ويقارن `lstat` و`fstat` والـHash قبل/بعد قراءة الأرشيف، ويبث Bytes المقبض إلى
`ZipInfo` بMetadata مضبوطة بدل `archive.write`، ثم يعيد فحص Snapshot الشجرة كاملًا.
النشر يستخدم Hard Link ذريًا no-clobber ولا يستبدل وجهة موجودة. بعدها يعيد Hash
للملف النهائي ويقارن Bytes المنشورة ببصمة الحجر، ولا يعيد إلا هذه البصمة النهائية.
عند الفشل لا يحذف الناتج إلا إذا أثبت القفل والهوية أنه ناتج هذه العملية؛ لا توجد
استعادة لناتج سابق لأن وجوده يمنع بدء العملية أصلًا.

يرفض Builder وVerifier، دون حساسية لحالة الأحرف، جميع متغيرات `.env` عدا أمثلة
`example`/`sample`/`template` المقصودة، و`.docker/config.json` و`.ssh`
و`.git-credentials` و`kubeconfig` وبيانات اعتماد AWS/Azure/GCloud وملفات
المفاتيح والشهادات مثل `.pem` و`.key` و`.p12` و`.pfx` وقواعد البيانات والكاش
والحالة المحلية. إذا بقي أي ملف محظور أو اسم مشتبه بأنه سر، يفشل التحقق والتغليف
ويطلب مراجعته يدويًا بدل حذفه بصمت.

الخيار `--allow-different-base` تجاوز يدوي **غير آمن**، ولا يعمل منفردًا: يجب تمرير
`--acknowledge-unverified-base` معه أيضًا. لا يعطل الفحص التمهيدي
الكامل ولا Verifier، لكنه يلغي إثبات مطابقة بصمة خط الأساس؛ لذلك الناتج لا يجوز
وصفه بأنه Verified أو مصدر كامل حقيقي متحقق، حتى إذا نجحت الفحوص البنيوية. يبقى
التطابق الدقيق مع SHA-256 المرجعي هو المسار الافتراضي.

## العزل التشغيلي

- `formatting-data`: أرشيفات المهارات وإصداراتها المستخرجة؛ يركبه API وعامل التنسيق، ولا يركبه OpenCode.
- `formatting-jobs-data`: Snapshot الإدخال والنتائج الدائمة لكل جيل تحت `jobs/<job-id>/executions/<execution-key>/`.
- `opencode-data`: بيانات اعتماد OpenCode فقط؛ إعداداته والكاش في `tmpfs` وليسا دائمين.
- يركب `opencode-runtime` فقط `opencode-data` ومساحة التبادل `formatting-execution-exchange`، ولا يركب بيانات المهارات أو المهام الدائمة. ينشئ `formatting-storage-init` علامة أمان ثابتة المحتوى داخل مساحة التبادل، ويتحقق منها العامل قبل عمليات التنفيذ ولا ينشئها API.
- يركب `formatting-dispatcher` مساحة التبادل نفسها وحدها لتشغيل Janitor، ولا يحصل على `opencode-data` أو أي إعداد أو اعتماد `OPENCODE_*`.
- يستثني Janitor مفاتيح الأجيال العاملة ذات Lease صالح أو حديث، ولا يحذف إلا مجلدات جيل صحيحة تجاوزت مهلة السماح، مع مسح محدود ورفض الروابط والعناصر الخاصة.
- قبل OpenCode يحفظ العامل `logs/execution-input-manifest.json` ببصمة وحجم النص وJSON العنوان و`opencode.json` وكل ملف مهارة بمساره النسبي، ثم يعيد جرد ملفات ومجلدات الإدخال/المهارة/السياسة قبل فحص أي مخرج. يجعل هذه المدخلات للقراءة فقط على الأنظمة الداعمة، بينما يبقى `output/` و`logs/` قابلين للكتابة. وبما أن OpenCode يعمل بالـUID نفسه حاليًا، يمكنه نظريًا إعادة `chmod` لو امتلك وسيلة تنفيذ؛ أداة Bash محظورة، لذلك الصلاحيات دفاع إضافي وليست حد عزل مستقلًا.
- `opencode-runtime` لا يحصل على `DATABASE_URL` أو `REDIS_URL`.
- تتصل البوابة وحدها بشبكة `edge` غير الداخلية، وتتصل مع API بشبكة `gateway`
  الداخلية ذات IPAM وعنوان بوابة ثابتين قابلين للضبط. لا تتصل API بـ`edge` ولا
  بأي شبكة خروج.
- يستخدم `opencode-runtime` شبكة `formatting-egress` للوصول إلى المزود وOAuth،
  ويستخدم `worker-1..5` شبكة `transcription-egress` للوصول إلى YouTube وDeepgram.
  لا يملك `api` ولا `formatting-worker` ولا `formatting-dispatcher` شبكة خروج مخصصة.

## ملاحظة اعتماديات المهارة

رفع ZIP لا يثبت حزم نظام أو Python تلقائيًا. أداة Bash العامة معطلة في سياسة
OpenCode المشددة؛ لذلك يجب أن تعمل المهارة بأدوات القراءة والتحرير المسموحة. أي
مجلد `scripts/` مرفوع يبقى مادة قراءة ولا يصبح قابلًا للتنفيذ. أي توسيع لقدرات
التنفيذ يحتاج مراجعة أمنية وتصميم صلاحية ضيقة وتعديلًا ثابتًا للصورة ثم إعادة البناء.

## نشر Coolify بأسرار تلقائية

للنشر الجديد استخدم الملف:

```text
docker-compose.yml
```

ينشئ Coolify تلقائيًا كلمات مرور PostgreSQL وRedis والمدير وOpenCode وسر الجلسة. أدخل فقط القيم الموضحة في:

```text
COOLIFY_ENVIRONMENT_VARIABLES_AR.md
```

ابدأ من `UPLOAD_NOW_README_AR.md` قبل الرفع.
