# معمارية نظام التنسيق المشتق

## المبدأ

التفريغ الأصلي ثابت. كل تنسيق كيان مشتق مستقل:

```text
Job (Deepgram) ──1:N── FormattingJob ──1:N── FormattingArtifact
                         │
                         ├── FormattingSkill version + SHA-256 snapshot
                         └── FormattingOutbox
```

## نقطة التكامل

تُقرأ نسخة TXT من تفريغ مكتمل فقط بعد حل مسارها تحت `EXPORTS_ROOT` والتحقق من
كل المكونات الموجودة ورفض الروابط الرمزية ونقاط إعادة التحليل والملفات الخاصة
والروابط الصلبة. يطبق `FORMATTING_INPUT_MAX_BYTES` قبل النسخ، وتحسب SHA-256
تدفقيًا، ثم يعاد التحقق من الحجم والبصمة للمصدر وSnapshot. تُنسخ النسخة ذرّيًا إلى:

```text
/data/formatting/jobs/<formatting-job-id>/input/transcript.txt
```

لا تعدّل الإضافة تنزيل YouTube، استدعاء Deepgram، مفاتيحه، طوابير `worker-1..5`، أو Transcript الأصلي.

## الخدمات

- `api`: الإعدادات، المهارات، OAuth، إنشاء المهام والتنزيل.
- `formatting-dispatcher`: ينشر سجل Outbox الدائم إلى Celery، ويتصل بشبكة `data` فقط، ويركب مساحة التبادل المؤقتة لتشغيل Janitor بلا بيانات اعتماد OpenCode.
- `formatting-worker`: Celery queue باسم `formatting` وتزامن واحد.
- `opencode-runtime`: خادم OpenCode وخدمة تحكم داخلية لفصل الحساب.
- `formatting-storage-init`: تهيئة الملكية والمسارات وإنشاء علامة أمان ثابتة المحتوى داخل مساحة التبادل، بلا شبكة.

## Volumes

- `formatting-data`: المهارات؛ يركبه API وعامل التنسيق، ولا يركبه OpenCode.
- `formatting-jobs-data`: الإدخال والمخرجات والسجلات الخاصة بالمهام.
- `opencode-data`: بيانات اعتماد OpenCode الدائمة فقط؛ الإعدادات والكاش في مسارات `tmpfs` مؤقتة.
- `formatting-execution-exchange`: مساحة التبادل التي يركبها عامل التنسيق وOpenCode وDispatcher. يركب Dispatcher هذه المساحة وحدها لأعمال Janitor بلا اعتماد OpenCode، بينما يركب OpenCode معها `opencode-data` فقط.

ينشئ API مجلدات المهارات والإصدارات والمهام الدائمة ويتحقق من سلامة كل مكوّن
منها من دون إنشاء مساحة التبادل أو علامتها. وحدها عمليات العامل على مساحة التبادل
تتطلب العلامة الموجودة في المسار الثابت `/data/formatting-execution`.

## الشبكات

- `data`: شبكة داخلية لـPostgreSQL وRedis وAPI والعمال، ولا ينضم إليها OpenCode.
- `formatting-control`: اتصال داخلي بين API/العامل وOpenCode.
- `gateway`: اتصال داخلي بين Nginx وAPI فقط، بعنوان Nginx ثابت قابل للضبط؛ يثق
  Uvicorn بهذا العنوان وحده في Forwarded headers.
- `edge`: شبكة غير داخلية للبوابة وحدها حتى يصل إليها Proxy المنصة. لا تنضم API
  إليها، ولذلك لا تحصل API على مسار خروج غير مقيد.
- `formatting-egress`: خروج OpenCode إلى مزود النموذج؛ لا ينضم إليها عامل التنسيق.
- `transcription-egress`: خروج `worker-1..5` فقط إلى YouTube وDeepgram.

شبكات `data` و`formatting-control` و`gateway` داخلية، أما `edge`
و`formatting-egress` و`transcription-egress` فليست داخلية. يجب اختبار دعم Coolify
لـIPAM والعنوان الساكن في Staging والتحقق من أن `GATEWAY_PEER_IP` داخل
`GATEWAY_NETWORK_SUBNET` ولا يتعارض مع شبكات المضيف؛ هذه بوابة تشغيل غير منفذة.

## جداول PostgreSQL

- `formatting_skills`: المهارات وإصداراتها وبصماتها.
- `formatting_settings`: النموذج ومستوى التفكير والمهارة الافتراضية.
- `formatting_jobs`: المحاولات والحالة والـSnapshot الثابت.
- `formatting_outbox`: التسليم الدائم من قاعدة البيانات إلى Celery.
- `formatting_artifacts`: ملفات النتائج وأنواعها وأحجامها وبصماتها.

## Snapshot

يحفظ كل Job:

- `source_job_id`
- `skill_id`, الاسم والبصمة
- النموذج وVariant التفكير
- SHA-256 لنسخة TXT
- رقم المحاولة
- `execution_generation` مستقل يُزاد ذريًا عند كل Claim أو Reclaim

ويتحقق العامل من بصمة النص وأرشيف المهارة مرة أخرى عند بدء التنفيذ. كما يطابق
اسم وslug سجل المهارة مع `skill_name_snapshot`، ويشترط أن يكون مسار الأرشيف هو
المسار المعنون بالبصمة تحت `skill_archives_root`. الأرشيف الموثق وحده كافٍ
للتنفيذ؛ لا يقرأ العامل `extracted_path` ولا يمنع فقده أو تلفه بدء المهمة.
يقرأ العامل ZIP المحدود الحجم تدفقيًا، ويتحقق من
بصمته إلى ذاكرة غير قابلة للتبديل، ثم يعيد تطبيق قواعد ZIP (ملف `SKILL.md` واحد،
مسارات آمنة، لا روابط أو عناصر خاصة، حدود العدد والحجم بعد الفك، وتطابق اسم
المجلد والمهارة) ويستخرج المهارة المختارة وحدها مباشرة إلى مساحة الجيل.
تبقى النسخة المستخرجة Cache للتخزين/العرض فقط. عند إعادة رفع ZIP مطابق، يتحقق API
منها ويستبدل Cache المفقود أو التالف ذرّيًا من الأرشيف الموثق بدل رفض الرفع.

## التسليم والاسترداد

يُنشئ API سجل `formatting_jobs` وسجل `formatting_outbox` في Transaction واحدة، ولا
يتصل بـCelery مباشرة. يطالب Dispatcher بالأحداث المستحقة باستخدام
`FOR UPDATE SKIP LOCKED`، ويستخدم معرّف Outbox نفسه كمعرّف Celery ثابت. لذلك لا
يؤدي تعطل Redis وقت طلب API إلى فقد المهمة أو تحويلها إلى `failed`.
ينشئ كل Claim رمز سياج UUID مستقلًا ويخزنه مع حالة `processing`. لا يستطيع
Dispatcher تعليم الحدث منشورًا أو رفضه أو إعادته إلى `pending` إلا بتطابق معرّف
الحدث والحالة والرمز معًا. يمسح الرمز عند كل حالة طرفية أو عودة إلى `pending`،
لذلك لا يستطيع مالك قديم تعديل حدث أعيد Claim له بعد انتهاء القفل.

يحمل التنفيذ Lease محدود المدة. ينشئ العامل مراقبته فور نجاح Claim، ويجدد الـLease
قبل المراحل الكبيرة وبعدها وأثناء تنفيذ OpenCode. إذا انتهت المهلة، يعيد Dispatcher
المهمة إلى `queued` وينشئ حدث Outbox جديدًا في Transaction واحدة. كما يصالح دوريًا
المهام القديمة في `queued` التي لا تملك حدثًا `pending` أو `processing`، ويحد عدد
الأحداث المنشورة في كل دورة حتى لا تستأثر الاستعادة بالخدمة.

كل Claim يزيد `execution_generation` ذريًا. تعتمد Heartbeat وتحديثات العامل والفشل
والإكمال وكتابة Artifacts على تطابق هذا الجيل وصلاحية الـLease، ولا يُستخدم
`celery_task_id` كسياج ملكية. تستخدم مساحة التبادل مفتاحًا مثل `<job-id>-g<generation>`،
وتُحفظ مخرجات وسجلات كل جيل تحت
`/data/formatting/jobs/<job-id>/executions/<execution-key>/`، لذلك لا يستطيع عامل
قديم حذف مساحة جيل أحدث أو استبدال نتيجته. ويلغي طلب الإلغاء أحداث Outbox غير
المنشورة ويمسح الـLease في Transaction الإلغاء نفسها؛ لا يصدر النظام أمر Celery
`revoke`، بل تلاحظ الرسالة المنشورة الإلغاء تعاونيًا وتصبح غير مؤثرة لأن Claim
يرفض الحالة الطرفية.

قبل استدعاء OpenCode يكتب العامل `logs/execution-input-manifest.json` ذريًا. يحتوي
بصمة SHA-256 والحجم لكل من `input/transcript.txt` و`input/source-title.json` و
`opencode.json`، وقائمة كل ملفات المهارة المختارة بمسارات نسبية وبصمات وأحجام.
يحتفظ أيضًا داخل عملية العامل بجرد الملفات والمجلدات وهوياتها. بعد رجوع OpenCode،
بما في ذلك مسار الخطأ، يعيد الجرد ويرفض أي ملف جديد أو محذوف أو مستبدل أو متغير
وأي رابط أو عنصر خاص، وذلك قبل فحص/نسخ المخرجات أو الإكمال. يصبح فشل النزاهة
`failed` فقط عبر تحديث الجيل والـLease المملوكين.

على POSIX يجعل العامل ملفات الإدخال والمهارة والسياسة للقراءة فقط ومجلداتها غير
قابلة للكتابة، مع إبقاء `output/` و`logs/` قابلين للكتابة. هذه طبقة دفاع إضافية:
يعمل OpenCode بالـUID نفسه حاليًا، ولذلك يمكنه نظريًا إعادة `chmod` لو توفرت له
قدرة تنفيذ؛ سياسة OpenCode تحظر Bash. يعيد التنظيف الآمن صلاحيات الشجرة بعد رفض
الروابط والعناصر الخاصة كي لا تمنع الحماية تنظيف العامل أو Janitor.

يبقى إيقاف جلسة OpenCode البعيدة نفسها عند إلغاء التنفيذ غير مثبت؛ الإلغاء ينهي
العميل المحلي المتصل ولا توجد في هذه الحزمة آلية موثقة لإجهاض جلسة بعيدة مجهولة.

يصالح العامل عند بدء المحاولة، وقبل استخدام أو نشر جيل دائم، حالات
`.output.copying` و`.output.previous` و`.logs.copying` و`.logs.previous`. يفحص
البنية والحدود والبصمات من الجذر الآمن. الهدف الصالح هو المرجع إذا كان موجودًا؛
وإذا فُقد الهدف أو تلف تُستعاد النسخة السابقة الصالحة أولًا، وإلا تُرقى نسخة
النسخ الصالحة الوحيدة. لا تُحذف النسخة الوحيدة التي يمكن التحقق منها، ولا تزال
نسخة مرحلية إلا بعد ثبوت هدف صالح. أما نسخة أولى مرحلية ناقصة لا تحقق عقد
المخرجات فليست نشرًا قابلًا للاسترداد ويمكن إزالتها لتسمح المحاولة التالية بإعادة
النشر. تبقى سلامة هذه المصالحة بعد انهيار عملية قاسٍ غير متحققة تشغيليًا؛ ما نُفذ
هو إصلاح ذاتي ساكن في المحاولة التالية، وليس إثبات Crash integration.

القيم الافتراضية في Compose هي Lease مدته 900 ثانية، ومصالحة `queued` بعد 300
ثانية، وحد أقصى 100 حدث Outbox في دورة Dispatcher الواحدة. يمكن ضبطها بواسطة
`FORMATTING_LEASE_SECONDS` و`FORMATTING_QUEUED_RECONCILE_AGE_SECONDS`
و`FORMATTING_OUTBOX_MAX_DISPATCH_PER_CYCLE`.

كل 300 ثانية افتراضيًا يطلب Dispatcher من PostgreSQL مفاتيح الأجيال `running`
ذات Lease غير منته أو منته حديثًا، ثم يمسح الجذر المباشر لمساحة التبادل بحد 10000
عنصر. يحفظ العلامة وهذه المفاتيح وكل مساحة أحدث من مهلة السماح (86400 ثانية)، ولا
يحذف إلا اسم `<job-id>-g<generation>` صحيحًا. أي جذر أو رابط أو ملف خاص أو رابط
صلب أو تجاوز للحد يفشل الدورة مع تحذير ويُبقي العنصر للمراجعة. الإعدادات هي
`FORMATTING_EXCHANGE_JANITOR_INTERVAL_SECONDS` و
`FORMATTING_EXCHANGE_JANITOR_GRACE_SECONDS` و
`FORMATTING_EXCHANGE_JANITOR_RECENT_LEASE_SECONDS` و
`FORMATTING_EXCHANGE_JANITOR_MAX_ENTRIES`.

بعد نجاح دورة الاسترداد والمصالحة والنشر يكتب Dispatcher طابعًا زمنيًا ذرّيًا في
`/tmp/formatting-dispatcher-heartbeat` افتراضيًا، ويمكن تغيير الملف بواسطة
`FORMATTING_DISPATCHER_HEARTBEAT_PATH` بشرط بقائه تحت `/tmp`. يقيس فحص الصحة
حداثته. أما فحص Scheduler
فيفحص أن لـTini ابنًا مباشرًا واحدًا يشغل `app.scheduler`؛ وهو فحص حياة عملية إلى أن يوفر
Scheduler الأصلي Heartbeat وظيفيًا.

لا تضيف هذه الحزمة FK من `formatting_jobs.source_job_id` إلى جدول المهام الأصلي،
لأن اسم الجدول ونوع المعرّف يعتمدان على مصدر التطبيق الذي ستُدمج فيه الحزمة. يبقى
هذا الربط مؤجلًا حتى يتوفر المصدر الأصلي، بينما FK الخاص بـOutbox مفعل مع
`ON DELETE CASCADE`.

## التحقق من المخرجات

الحالة لا تصبح `completed` بناءً على كلام الوكيل. العامل يتأكد من:

- وجود `output/result.md`، وأنه UTF-8 صالح وغير فارغ بعد فك الترميز.
- وجود `output/manifest.json` ككائن JSON بلا مفاتيح مكررة، وأن `status` يساوي
  `completed` أو `success`، وأن `primary_output` يساوي `result.md` تمامًا، وأن
  `summary` نص آمن غير فارغ.
- تطابق قائمة `outputs` بلا تكرار مع كل الملفات الفعلية تحت `output/`، بما فيها
  `manifest.json` نفسه، مع رفض المسارات المطلقة أو المتراجعة أو غير الآمنة.
- صلاحية UTF-8 لكل ملفات `.md` و`.txt` و`.html` ورفض محارف التحكم C0/C1 غير
  النصية لمنع تمرير محتوى ثنائي بامتداد نصي.
- بقاء مساحة التنفيذ الحية كاملة، بما فيها النص والمهارة والإعدادات والمخرجات والسجلات، ضمن حدَي عدد العناصر والحجم، مع رفض الروابط والملفات الخاصة أثناء التشغيل.
- ملاءمة خط الأساس الثابت (Snapshot الإدخال والمهارة وإعداد OpenCode) للحدود نفسها قبل تشغيل OpenCode.
- عدم وجود Symlink في الملفات المسجلة.
- الامتدادات المسموحة فقط.
- حدود العدد والحجم الفردي والإجمالي.
- صحة JSON.
- رأس PDF.
- بنية DOCX وفتحها بواسطة `python-docx`.
- SHA-256 لكل Artifact، ويعاد فحص البصمة عند التنزيل.

## سعة التخزين الدائم

قبل إنشاء Snapshot أو سجل مهمة جديد، يمسك API قفل PostgreSQL استشاريًا مخصصًا
للتخزين. يفحص `skills_root` و`jobs_root` كلًا على حدة بتجوال تدريجي لا يجمع
المسارات في الذاكرة؛ ولا يفحص `FORMATTING_ROOT` الأب، لأن `jobs_root` Volume مركب
داخله بصورة منفصلة ولأن فحص الأب والابن قد يكرر حسابه. يرفض الروابط ونقاط إعادة
التحليل والملفات الخاصة والروابط الصلبة، ويتوقف فور تجاوز الحد.

يحجز لكل مهمة نشطة ومهمة جديدة مجموع `FORMATTING_INPUT_MAX_BYTES` و
`FORMATTING_OUTPUT_MAX_TOTAL_BYTES` و`FORMATTING_EXECUTION_LOG_MAX_BYTES`. وقبل
تثبيت مهارة، وتحت القفل نفسه، يحجز حجم ZIP المرفوع مضافًا إلى
`FORMATTING_SKILL_MAX_UNPACKED_BYTES` مع إبقاء حجوزات المهام النشطة. يقارن المستخدم
والمحجوز مع `FORMATTING_STORAGE_MAX_BYTES` (افتراضيًا 20 GiB)، ويرجع API `507` عند
نفاد السعة و`422` عندما يكون أحد الجذرين غير آمن.

هذه بوابة Admission محافظة وليست سياسة Retention أو Quota تعيد المساحة تلقائيًا.
لا تحذف المهام المكتملة أو تاريخ محاولاتها أو Artifacts آليًا. وتبقى سجلات قاعدة
البيانات وSnapshot الإدخال الدائم للمهام الفاشلة والملغاة، وكذلك أي جيل دائم نُشر
قبل الحالة الطرفية. أما مساحة التنفيذ المؤقتة وملفاتها غير المنشورة فتُنظف بأفضل
جهد بعد الفشل أو الإلغاء، ويسترد Janitor المساحات اليتيمة القديمة فقط، فلا تعد سجل احتفاظ. لا توجد حاليًا مهمة تنظيف تلقائي
للتاريخ الفاشل أو الملغى أو المكتمل؛ الحذف المتعمد مؤجل إلى سياسة احتفاظ صريحة.
يمرر Compose متغيرَي الإدخال والتخزين إلى `api` و`formatting-worker` معًا حتى لا
تختلف إعدادات الأدوار التي تحمّل `FormattingConfig`.

## حدود الثقة

المهارات تعليمات وبرمجيات قابلة للتنفيذ. لذلك:

- الإدارة محصورة بالمستخدم الإداري.
- لا تُرفع مهارات مجهولة المصدر.
- أداة Bash معطلة داخل مساحة OpenCode؛ المهارات التي تتطلب تشغيل سكربتات عامة غير مدعومة في الوضع المشدد.
- وجود `scripts/` في ZIP لا يمنح صلاحية تنفيذ؛ تبقى الملفات مادة قراءة للوكيل.
- لا تمنح شبكة OpenCode وصولًا إلى PostgreSQL أو Redis، مع بقاء خروج المزود متاحًا لخدمة OpenCode نفسها.
- لا يُركب Docker Socket، ولا تُمرر أسرار PostgreSQL/Redis إلى OpenCode.

## أعمال محجوبة

- لم تُنفذ حاويات أو mounts منفصلة لكل مهمة؛ يتطلب ذلك تغيير Compose ونموذج التشغيل.
- لم تُنفذ آلية إجهاض جلسة OpenCode البعيدة؛ الإلغاء التعاوني المحلي هو المتاح فقط.
- لم تُنفذ سياسة تنظيف احتفاظ دائمة؛ التاريخ الفاشل والملغى والمكتمل لا يحذف تلقائيًا.
- ما زال المصدر الأصلي الكامل وFK من `source_job_id` وحذف البيانات وفق سياسة احتفاظ محجوبًا حتى الدمج النهائي.
